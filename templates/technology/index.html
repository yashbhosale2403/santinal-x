Section B

Device-Specific Sanitization Methods

Why different media architectures require custom hardware command families.

Magnetic Media

1. HDD / Magnetic Drive

Why Different:

Data stored as magnetic domain alignments on platters accessed sequentially by LBAs.

Recommended Approach:

Controlled raw binary sector overwriting (`os.fsync()`) or ATA SECURE ERASE hardware pulse.

Command Family: ATA SECURE ERASE / os.write(0x00)
Verification:

Sector zero sampling at 0%, 25%, 50%, 75%, 100% offsets.

Remanence Note: Basic overwrite does NOT require AES/RSA/SHA-256. SHA-256 is an integrity hash, not an erasure algorithm.
NAND Flash

2. SATA SSD

Why Different:

FTL Wear Leveling & Garbage Collection mean ordinary LBA overwriting does NOT guarantee physical NAND block sanitization.

Recommended Approach:

ATA Sanitize, Block Erase, or Cryptographic Erase if supported by FTL controller.

Command Family: ATA SANITIZE / BLOCK ERASE / CRYPTO PURGE
Verification:

Controller status code check + addressable sector sampling.

FTL Decision Flow: ATA Sanitize → Block Erase OR Cryptographic Erase (only when drive reports capability).
PCIe NVMe

3. NVMe SSD

Why Different:

High-speed NVMe controller manages hardware queues, namespaces, and native format capabilities.

Recommended Approach:

NVMe Format NVM command with User Data Erase (SNASE=1) or Cryptographic Erase (SNASE=2).

Command Family: nvme format /dev/nvmeXn1 -s 1|2
Verification:

NVMe controller completion status code + sector sampling verification.

NVMe Execution Flow: NVMe SSD → Capability Detection → User Data Erase / Cryptographic Erase → Verification.
Removable Flash

4. USB Flash Drive

Why Different:

USB Mass Storage bridge hides internal flash controller capabilities. Generic USB does not guarantee one universal method.

Recommended Approach:

Multi-offset full binary zero pass + sector verification. Query USB capabilities dynamically.

Command Family: USB SCSI PASSTHROUGH / BINARY OVERWRITE
Capability Detection Required: SENTINEL-X detects device capabilities dynamically before recommending sanitization.
Memory Card

5. SD / microSD Card

Why Different:

SD cards rely on raw flash microcontrollers; ordinary logical overwriting may leave unmapped blocks intact.

Recommended Approach:

SD ERASE command (CMD38) if supported by host controller, or full zero fill + verification.

Command Family: SD CMD38 ERASE / RAW ZERO FILL
Assurance Note: Logical overwriting cannot guarantee physical NAND sanitization without low-level SD bus ERASE support.
SED / Crypto Drive

6. Encrypted Storage

Cryptographic Erase Flow:

Plaintext → Encryption → Ciphertext → Encryption Key sanitization → Data permanently unreadable.

Recommended Approach:

Sanitize Media Encryption Key (MEK) inside hardware Security Subsystem.

Command Family: OPAL CRYPTO ERASE / MEK RE-KEYING
Prerequisite Condition: Only appropriate when target drive architecture natively implements hardware-level encryption (SED).
Section C

What is a Sanitization Algorithm vs What is Not?

Clearing common misunderstandings between data sanitization, cryptographic hashing, and immutable ledger logging.

🧹 SANITIZATION

Destroys or renders user data inaccessible using media/device-specific techniques (sector zeroing, ATA Secure Erase, NVMe Format, Crypto Erase).

NOT AES(), SHA256(), OR RSA()

🔐 SHA-256 HASHING

Creates a 256-bit cryptographic fingerprint of files, evidence, and audit records. Proves integrity and detects post-operation alteration.

INTEGRITY FINGERPRINT, NOT ERASURE

⛓️ IMMUTABLE LEDGER

Records execution hashes in a tamper-evident chain (`Hash = SHA256(Event + PrevHash)`) so any retroactive modification is immediately flagged.

AUDIT ANCHOR, NOT DATA STORAGE

Section E

Analytical Confidence Scoring Model

Confidence score is an analytical estimate based on structural integrity and NOT proof of legal authenticity.

Recovered File: evidence_001.jpg
Magic Header Match:✓ MATCH (+25%)
Structure Header Validation:✓ VALID (+25%)
Footer / EOF Signature:✓ FOUND (+20%)
Decoder Parser Test:✓ PASSED (+15%)
Fragment Sequence Consistency:✓ HIGH (+9%)
CONFIDENCE SCORE: 94% — HIGH CONFIDENCE

Scoring Weight Distribution:

  • Magic Signature Match (+25%): Validates raw binary start offset (e.g. `FF D8 FF` for JPEG).
  • Internal Header Parsing (+25%): Confirms valid SOF0 markers, EXIF header tags, or PDF xref table offsets.
  • EOF / Trailer Match (+20%): Detects end-of-file bytes (e.g. `FF D9` for JPEG or `%%EOF` for PDF).
  • Decoder Validation (+15%): Passes binary stream into image/document decoders without crash.

Section H

Immutable Ledger Architecture

SENTINEL-X does NOT store raw evidence or recovered files on blockchain. Only cryptographic hashes and operation metadata are anchored.

Anchored Metadata Structure:

  • • Operation ID (`UUIDv4`)
  • • Event Hash (`SHA-256`)
  • • PDF Report Hash (`SHA-256`)
  • • ISO Timestamp (`UTC`)
  • • Ledger Block Reference (`Index + PrevHash`)

Verification Match / Mismatch:

✓ MATCH: SHA256(Current Audit) == Ledger Entry Hash
🔴 MISMATCH: SHA256(Current Audit) != Ledger Entry Hash
Section I

NIST SP 800-88 Rev. 2 Policy Model

Standardized sanitization category definitions for media disposition.

Category 01

CLEAR

Overwrites logical blocks using basic read/write interface against non-advanced data recovery tools.

Category 02

PURGE

Executes controller-level ATA Sanitize or NVMe Format commands rendering target data unrecoverable even in laboratory environment.

Category 03

CRYPTOGRAPHIC ERASE

Sanitizes the Media Encryption Key (MEK) on self-encrypting drives (SED), rendering ciphertext permanently unreadable.

Category 04

DESTROY

Physical destruction of target media platters or NAND chips via disintegration, incineration, or degaussing.

NIST Assurance Disclaimer:

"Sanitization assurance depends on media type, device capabilities, selected technique, and post-operation verification." Reference label: NIST SP 800-88 Rev. 2.
